# Role and question creation

Creation logic lives in Application. `RoleService.CreateAsync` authorizes the
caller, validates the request, checks name uniqueness and saves the new role.
`QuestionService.CreateAsync` does the same for a question: it validates the
request, checks the answer shape for the question type, and saves the question
with its answers.

## Responsibilities

| Type / namespace | Responsibility |
| --- | --- |
| `Services.RoleManager.IRoleService` | Creates and saves a `Role` from `CreateRoleDto` after authorization, validation and name-uniqueness checks. Custom role names remain supported. |
| `Services.QuestionManager.IQuestionService` | Creates and saves a `Question` and its `Answer` entities from `CreateQuestionDto` after authorization, validation and answer-shape checks. |
| `DTOs.QuizManager.Questions.CreateQuestionAnswerDto` | Carries answer text, correctness and activity when creating a question. IDs and navigation properties are generated by the service. |

All namespaces above start with `Quizapp.Application.`. Role and question
creation each have one workflow and stay in their service.

## Question creation rules

These are the creation policies for this implementation. They are not scoring
algorithms.

| Question type | Active answer requirements |
| --- | --- |
| `SingleChoice` | At least two options; exactly one correct. |
| `MultipleChoice` | At least two options; at least one correct. |
| `TrueFalse` | Exactly two options; exactly one correct. Labels are supplied by the caller and can be localized. |
| `FillInTheBlanks`, `ShortAnswer` | At least one accepted answer; all active answers must be marked correct. |
| `LongAnswer` | Reference answers are optional; any active references must be marked correct. |

`CreateQuestionAnswerDto.IsActive` defaults to `true`. Inactive answers are
preserved in the created graph but do not count toward these requirements.
The rules also apply when creating an inactive question. Every supplied answer,
including inactive ones, must have non-empty text within the existing field limit.
Text comparison, grading, partial credit and manual review are not implemented here.

The service generates a new ID for the question and every answer. Each answer''s
`QuestionId` and `QuestionNavigation` point to the newly created question. No client
answer IDs or question IDs are accepted by the nested creation DTO.

## Create requests directly

`AddApplication()` registers the services and validators with scoped lifetime.
The following snippets assume injected variables named `roleService` and
`questionService`. Both require an authenticated administrator and persist the
new entity.

```csharp
using Quizapp.Application.DTOs.RoleManager;

var role = await roleService.CreateAsync(new CreateRoleDto
{
    RoleName = "Question Reviewer",
    Description = "Reviews question content",
    IsActive = true
});
```

```csharp
using Quizapp.Application.DTOs.QuizManager.Questions;
using Quizapp.Domain.Enums;

var question = await questionService.CreateAsync(new CreateQuestionDto
{
    Content = "Which keyword declares a class in C#?",
    QuestionType = QuestionType.SingleChoice,
    Level = QuestionLevel.Easy,
    IsActive = true,
    Answers =
    [
        new CreateQuestionAnswerDto { Text = "class", IsCorrect = true },
        new CreateQuestionAnswerDto { Text = "namespace", IsCorrect = false }
    ]
});
```

Object initializers assign the mutable DTO properties directly. Unset properties
use DTO defaults. Both services run FluentValidation; question creation also
checks the answer shape. See [DTO construction](dto-construction.md) for
collection-copying guidance. Invalid request data produces `ValidationException`.
`AddApplication()` can be called repeatedly without duplicating its own
registrations.

A new question type needs a `QuestionType` value and a branch in the answer-shape
check in `QuestionService`, plus tests for the new rules. Persistence changes, if
any, require a separate migration review.
